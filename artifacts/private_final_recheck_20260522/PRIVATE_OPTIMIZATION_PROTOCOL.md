# Private Optimization Protocol - 2026-05-22

## Goal

Optimize selected final submissions for the private leaderboard, not the public leaderboard.

The actual private labels are unknowable before the deadline. Therefore the only legitimate strategy is robust private-proxy optimization:

- simulate many public/private splits on labeled test-like validation rows
- stress by domain, procedure type, query length, and gold-count profile
- select a portfolio of finalists that fail differently
- reject public-only hillclimb variants unless they improve the private proxy

## Non-Negotiable Rule

A candidate is not promotable as a private final unless it has both:

1. a test CSV
2. a matching validation CSV generated by the same recipe

Public-only edits can be useful probes, but they cannot estimate private performance.

## Current Best Private Objective

Final selection should maximize best-of-final-submissions private score, not single public score.

For a two-final portfolio, the private objective is:

```text
score(pair, split) = max(private_score(candidate_a), private_score(candidate_b))
```

Then we evaluate that over many simulated private splits.

## PhD Mathematician Corrections

The public leaderboard score is a biased estimator after adaptive submissions. Once a candidate has been selected through many public-score observations, its visible score should be treated as an order statistic, not an unbiased estimate of generalization.

The private proxy must therefore use robust dominance, not point estimates:

- optimize pair-level `max(score_a, score_b)`, not individual score
- require stability across split schemes, not one lucky split
- prefer high lower-tail performance: `p10_private`, `worst_private`, and minimum `p_contains_private_winner`
- penalize high pair overlap because correlated candidates do not buy a second final-submission draw
- reject test-only candidates because they have no unbiased private proxy

Promotion is a dominance test. A challenger does not replace the current pair unless it improves the baseline on at least three of:

1. higher average `p_contains_private_winner`
2. higher minimum `p_contains_private_winner`
3. equal or higher exact/enumerated `p10_private`
4. equal or better diversity/failure-mode separation

This avoids optimizing mean score while silently worsening the lower tail.

## PhD Physicist Corrections

Treat each submission as a state in a rugged energy landscape. Public-LB hillclimbing moves a candidate toward a public-half basin. It can lower public energy while increasing private fragility.

The useful physical quantities are:

- overlap/order parameter: test atom Jaccard
- basin diversity: whether two finals fail on different query/citation families
- replica stability: whether the same pair wins under random, domain, procedural, length, and leave-bucket split replicas
- low-temperature/adversarial behavior: exact half-val enumeration and lower-tail score

Interpretation:

- `Jaccard > 0.98` versus a public peak means the candidate is in the same basin and is not an independent hedge.
- A high-public chain with only a few removals is a local relaxation of the public basin, not a new phase.
- The best final pair is the one that remains near the ground state across many split replicas, not the one with the lowest public energy.

This is why `intersect_bold7h_33028 + fusion_samesrc03_32274` remains favored: it has materially lower overlap and repeatedly survives split replicas.

## Promotion Gate

A new candidate pair can replace the current private pair only if it beats the current pair on at least three of these four dimensions:

1. higher average `p_contains_private_winner`
2. higher minimum `p_contains_private_winner` across schemes
3. equal or higher adversarial `p10_private`
4. lower pair Jaccard or clearly different failure mode

It must also avoid all hard failures:

- no missing validation CSV
- no notebook-reproduction breakage
- no pure public-leaderboard chain with `Jaccard > 0.98` to public peak
- no known failed-removal trap
- no two-final pair with pair Jaccard above `0.95` unless it has overwhelming private-proxy dominance

## How To Generate Private-Oriented Candidates

Allowed directions:

- full-recipe variants that produce both val and test
- conservative intersection/precision variants with validation companion
- recall hedge variants that are intentionally different from public peak
- domain hedges based on val/test-like legal structure, not public score
- low-public-score but high-diversity private-survival candidates

Avoid:

- single-citation public hillclimb chains
- variants that only remove citations from public-active rows
- near-duplicates of the public peak
- candidates selected because public score increased
